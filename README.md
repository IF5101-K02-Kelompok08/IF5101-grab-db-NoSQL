# IF5101 Grab NoSQL Database Project

A NoSQL database implementation for the **Grab Mobility & Fulfillment** domain, developed as part of the IF5101 Data Management course at Institut Teknologi Bandung.

This project explores two database technologies:

- **Apache CouchDB:** Document-oriented database for persistent data storage.
- **Memcached:** In-memory key-value store for caching frequently accessed data.

The repository includes database configurations, a reproducible synthetic dataset, functional tests, and benchmarking utilities.

**Benchmark directories:**

## 2. Setup

### Prerequisites

- Python 3.13+
- [uv](https://docs.astral.sh/uv/)
- Docker with Docker Compose
- Git

Clone and install dependencies:

```bash
git clone https://github.com/IF5101-K02-Kelompok08/IF5101-grab-db-NoSQL.git
cd IF5101-grab-db-NoSQL
uv sync --frozen
```

Create `.env` from `.env.example` and configure the CouchDB credentials.

```bash
# Linux/macOS
cp .env.example .env

# Windows PowerShell
Copy-Item .env.example .env
```

Start both databases:

```bash
docker compose --env-file .env -f docker/compose.yaml up -d --build
```

| DBMS | Local endpoint |
|---|---|
| CouchDB | `http://127.0.0.1:5984` |
| Memcached | `127.0.0.1:11211` |

Stop the containers without deleting persistent data:

```bash
docker compose --env-file .env -f docker/compose.yaml down
```

## 3. Canonical Dataset

Both implementations use the same synthetic dataset, adapted from the [Part 2 SQL repository](https://github.com/IF5101-K02-Kelompok08/IF5101-grab-db-SQL).

The `nosql` profile uses **2× the Part 2 large dataset**, with random seed `42`.

| Entity | Records |
|---|---:|
| Service orders | 2,000,000 |
| Customers | 200,000 |
| Driver partners | 100,000 |
| Locations | 400,000 |
| Merchant outlets | 60,000 |

Other entity counts follow the generator's simulation logic.

### Generate and Verify

```bash
uv run --no-sync python scripts/generate_data.py --profile nosql --output-dir data/canonical
uv run --no-sync python scripts/verify_canonical.py
```

The generator produces 13 CSV files. These are Git-ignored due to their size.

The committed `data/canonical/manifest.json` contains row counts, schemas, file sizes, and SHA-256 checksums. Verification ensures that locally generated files match this reference.

To intentionally regenerate the manifest after changing the dataset:

```bash
uv run --no-sync python scripts/generate_manifest.py
```

**Do not regenerate the manifest merely to bypass a verification failure.** Any changes to the reference dataset should be agreed upon by the team.

Each DBMS implementation is responsible for transforming the canonical CSV files into its own logical data model while preserving relevant data semantics.

## 4. Testing and Benchmarking

### Smoke Tests

Smoke tests verify database connectivity and basic CRUD/key-value operations.

Load `.env` variables into your shell before running Python tests.

**PowerShell:**

```powershell
Get-Content .env | Where-Object { $_ -match '^[^#=]+=.*' } | ForEach-Object {
    $parts = $_ -split '=', 2
    [Environment]::SetEnvironmentVariable($parts[0], $parts[1], 'Process')
}
uv run --no-sync python tests/smoke_test.py
```

**Linux/macOS:**

```bash
set -a
. ./.env
set +a
uv run --no-sync python tests/smoke_test.py
```

Smoke tests also run automatically through GitHub Actions on pushes and pull requests to `main`.

### Benchmark Runner

The shared runner measures DBMS operation latency through adapters in `benchmarks/adapters/`.

Each adapter implements `create_scenarios()` with the following contract:

| Method | Responsibility |
|---|---|
| `setup()` | Prepare an equivalent initial state |
| `execute(ctx)` | Execute the measured operation |
| `validate(ctx, result)` | Check result correctness |
| `teardown(ctx)` | Clean up or restore test data |

Only `execute()` is timed. The default procedure uses **one warm-up and three measured runs**.

**PowerShell:**

```powershell
uv run --no-sync python -m benchmarks.run `
  --adapter benchmarks.adapters.couchdb_example `
  --adapter benchmarks.adapters.memcached_example `
  --dataset-size 2000000
```

**Linux/macOS:**

```bash
uv run --no-sync python -m benchmarks.run \
  --adapter benchmarks.adapters.couchdb_example \
  --adapter benchmarks.adapters.memcached_example \
  --dataset-size 2000000
```

Outputs are written to `benchmarks/results/`:

- `runs.csv`: Individual execution times, validation statuses, and errors.
- `results.json`: Scenario summaries, result previews, and latency statistics.

After verifying the results and experimental conditions, copy the final outputs into `benchmarks/published/` for version-controlled reporting.

**Note:** The example adapters use temporary data. They demonstrate the benchmark interface but do not measure performance against the full canonical dataset. The dataset size argument is metadata, not an automatic database loader.

See [Benchmark Methodology](benchmarks/metodologi_benchmark.md) for the full evaluation procedure.
